## Fixes Needed To Make Baseline Runnable

1. External LECT identity verification was too strict for shallow runtime reuse.
   The d23 warm cache stores a split schedule generated to depth 64, while the
   online staged runner uses depth 40. Reuse is valid when the stored split
   schedule has the same prefix through the requested runtime depth. The
   database open path now allows this prefix-compatible case.

2. Worker oracle sessions reused `/tmp/lectdb_sbf_session_<id>` across process
   restarts. A previous crash could leave a worker DB manifest with a different
   root domain, causing later runs to fail with `root domain fingerprint differs`.
   Worker temp directories now include the process id and are removed before use.

3. `LectReadSnapshot` lazily populated an exact-box lookup cache without a lock.
   Baseline external snapshot reuse with 8 worker threads could race on this
   `unordered_map` and segfault. The exact-box cache is now mutex-protected.

4. `run_shelf_sbf_anytime.py` now writes the output artifact after every
   completed stage with `status="partial"` and rewrites it as
   `status="completed"` at the end. A late crash no longer discards earlier
   stage rows.

The 3-seed artifact should be read carefully: the current anytime runner
appends five records per seed instead of aggregating duplicate stage IDs. The
table above therefore splits the records into consecutive five-stage chunks.

The reason is semantic rather than a cache bug. `link` correctly selects
`EnvelopeType.LinkIAABB` and `support_hull` correctly selects
`EnvelopeType.SupportHull`; the rows use the same audit and query pipeline.
However, the reported path length is the extracted waypoint/segment-edge path
from the box graph, not an optimization objective for envelope tightness. AABB
happens to create a graph and segment-edge set that gives shorter audited
waypoints for AS->TS and TS->CS in this shelf seed. Thus the current experiment
can support "baseline is faster along the curve due to d23 replay", but it
cannot support "SupportHull baseline has better path quality than AABB" under
the present query/connector semantics.

One additional diagnostic separates the geometric-envelope invariant from the
generated-graph claim. For the same endpoint payload, the collision code first
runs the same padded link-AABB broad phase for LinkIAABB and SupportHull, so a
box that is free because all LinkIAABB boxes reject should also be free under
SupportHull. But the planner does not build an exhaustive canonical graph. It
adaptively chooses, reserves, and connects boxes under a fixed budget. Rebuilding
the s15 balanced stage and comparing exact joint-interval keys gives:

| row | generated boxes |
| --- | ---: |
| baseline SupportHull | 160 |
| AABB | 160 |
| exact interval keys common to both | 92 |
| AABB boxes absent from generated SupportHull graph | 68 |
| SupportHull boxes absent from generated AABB graph | 68 |

Several AABB query paths also use boxes absent from the generated SupportHull
graph; for example, the AABB TS->CS sequence has 10 boxes and only 8 exact
interval keys appear in the SupportHull graph. Therefore the false implication
is "SupportHull can certify every AABB-free box" -> "the finite generated
SupportHull graph contains the finite generated AABB graph." The latter would
require a shared exhaustive candidate tree or an explicit refinement step that
materializes the AABB graph's boxes under the SupportHull oracle.

The same rebuilt-forest diagnostic gives concrete evidence for the more
conservative-AABB mechanism. At equal stage budgets, AABB certifies a much
smaller total joint-volume and spends more materializations, which means the
budget is being consumed by a different set of smaller local boxes rather than
by the larger boxes accepted by SupportHull:

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| seed | 32 | 32 | 26 | 6.34e-5 | 3.63e-5 | 4.50e-5 | 1.80e-5 |
| fast | 96 | 96 | 69 | 1.10e-4 | 6.03e-5 | 8.64e-5 | 3.67e-5 |

The balanced stage is the clearest path-quality reversal. SupportHull has two
segment edges added, while AABB has four. For TS->CS at balanced, SupportHull's
current query path is 5.580 rad with no segment edge, whereas AABB's path is
3.123 rad with one segment edge; only 8 of the 10 exact AABB box intervals in
that query sequence exist in the SupportHull graph. Thus the shorter AABB path
is not evidence that AABB is geometrically tighter. It is evidence that the
more conservative AABB run generated a different local graph and a useful
segment edge that the finite-budget SupportHull run did not materialize.

## Why The Results Do Not Fully Match The Original Narrative

1. Baseline is not clearly faster in cumulative build time.
   External evidence reduces endpoint materializations from about 3021 to 1278
   and lowers cumulative query time, but the high-stage build remains dominated
   by grower/connector wall time. In this run baseline connector time is higher
   than the no-cache row, masking the oracle reuse benefit.

2. AABB has the shortest reported path length, but this is not strong evidence
   that AABB is a better planner. Query length is not the build objective. The
   graph query uses a representative-point A*/Dijkstra cost plus segment-edge
   costs, then reports the extracted waypoint path. Connector successes and
   segment edges vary by row, so path length is partly an artifact of graph and
   connector structure. AABB also has much smaller committed volume, consistent
   with more conservative certification, even though it happened to produce a
   shorter path in this seed.

3. Current non-baseline rows are not one-factor ablations relative to baseline.
   By design for this run, every non-baseline row also disables external cache
   and endpoint evidence cache. This is useful for the requested comparison but
   should not be presented as a clean mechanism ablation table unless paired
   cached versions are also run.

4. The shelf case is too easy for success-rate discrimination. Every row is
   5/5 with zero repairs. The remaining differences are path length, connector
   behavior, and oracle counters. That is too weak for a narrative claiming one
   full method is consistently superior unless the paper frames Exp.4 as a
   mechanism/cost attribution study.

## Current Strict Interpretation

The code now supports the intended baseline cache reuse semantics: a deeper
stored LECT schedule can serve a shallower online runtime when the split prefix
matches. The latest data supports a narrower claim:

- warm external evidence substantially reduces online endpoint materialization;
- warm external evidence lowers query time in this run;
- build time is not yet dominated by endpoint materialization, so end-to-end
  speedup is not reliably visible in this easy shelf setting;
- path length should not be used as the main evidence for envelope superiority
  without controlling connector randomness and graph structure.

with its `lect_snapshot`. The cache manifest confirms `prewarm_depth=23`,

For this study the runner was extended with

The recommended operating point is therefore:

- d23 snapshot external evidence enabled;
- `--coverage-anchor-preset iris8`;
- `--frontwave-bootstrap-depth 15`;
- `--frontwave-bootstrap-boxes 240`;
- `--max-boxes 320`;
- `--component-connect-prob 0.0`;
- build connector enabled with BiRRT segment edges;
- `--connector-rrt-step-size 0.25`;
- `--connector-max-pairs-per-gap 3`;
- `--connector-pave-max-chain 0`;
- `--segment-edge-policy normal`;
- `--final-ompl-simplify-time-s 0.05`.

This setting keeps the tree shallow and small, reaches 5/5 audited shelf
queries without repair, and stays around the 1 s regime while producing the
shortest median path among the tested d23+segment configurations. More boxes
and heavier component-connect growth do not improve the current path metric
reliably; they mainly add grower/frontier-search time. The smaller BiRRT step
variant also does not help: it roughly doubles connector time and gives worse
median path length.

- Segment edges are essential for the shallow tree: the no-segment control

- The eight-anchor design improves path quality relative to the legacy five

- The 0.05 s final simplification is a useful low-cost quality step: it reduces

  via external-hit/materialization counters, not oversold as a large wall-time

- Increasing the coverage budget to d18/b900 increases time to 2.259 s and does
  not beat the recommended row's path median. Under the current query semantics,
  the best operating point is therefore the shallow d15/b320 row with segment
  connector and 0.05 s final simplification.

## Current Explanation For Narrative Mismatch

There are two separate issues, not one:

1. Paper-facing RBF-only cache rows were mostly a documentation/generator
   mismatch. The authoritative JSON supports external reuse in the Shelf warm
   rows, but stale generated tables and stale plan text made it look like the
   result contradicted the manuscript.
2. The newer Exp.4 ablation run is a different protocol. It uses a d23 warm
   baseline and intentionally disables external evidence and endpoint evidence
   cache for non-baseline rows. That run supports cache-materialization
   attribution, but it does not support a broad one-factor superiority claim for
   baseline path length or end-to-end build time.

So the strongest defensible narrative is:

- RBF/LECT replay is real and visible in external-reuse/materialization
  counters.
- In the Shelf workload, replay does not guarantee a large wall-time speedup
  because connector/grower/validation time dominates.
- Path length differences in Exp.4 are graph/connector dependent and should be
  secondary evidence unless the experiment is rerun with paired cache controls
  and multiple seeds.
